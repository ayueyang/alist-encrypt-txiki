# 背景与加密原理

> 本文内容整理自上游 [alist-encrypt](https://github.com/traceless/alist-encrypt) 的项目说明，
> 上游采用 ISC 许可。文中性能数据来自上游作者的实测记录。

## 需求背景

AList 是一个支持多种存储与云网盘、支持网页浏览并提供 WebDAV 服务的应用。国内云盘普遍存在
敏感资源被删除的问题，直接的规避方案是加密后上传——但这样往往就不能在线播放视频了。

alist-encrypt 在上传时加密、下载时解密。由于采用的是**流加密**方案，可以边解密边播放，
因此加密的视频依然能够在线播放，图片也能在线查看。它既可以在网页中上传文件，也可以配合
WebDAV 客户端使用，并优先适配 AList。

适用场景：对文件隐私有要求、需要防止云盘扫描删除、同时要求实时播放与下载。

## 加密原理

项目的早期想法记录在 [traceless/tlf-encryption](https://github.com/traceless/tlf-encryption)，
其中描述了 MIX 混淆算法的实现、代理服务的实现思路，以及基础版本代码，可作为学习参考。

MIX 的本质是混淆：它不足以抵抗基于文件特征的暴力破解，因此不推荐用于真正的加密需求，
仅在性能极度受限且不关注保密强度的场景下才有意义。

## 算法选择

当前实现提供三种 `encType`：

| 算法 | 定位 | 说明 |
|---|---|---|
| `aesctr`（默认） | 推荐 | AES-CTR 流式加密。速度最快，安全性好。推荐 armV8 以上，或支持 AES 指令的 x86 机器 |
| `rc4` | 备选 | RC4 流加密。理论安全性略有瑕疵但可忽略；适合 CPU 不支持 AES 指令的设备，速度同样很快 |
| `mix` | 不推荐 | 早期混淆方案，强度不足，仅作为兼容保留 |

**结论**：绝大多数设备都应使用 AES-CTR。近年设备的 CPU 基本都支持 AES 指令，
它在性能与安全两端都更优；只有在确实不支持 AES 指令的老旧设备上才考虑 RC4。

## 性能参考

上游在 CPU `s905l3a` 上的实测数据：

| 算法 | 吞吐 |
|---|---|
| RC4 | 约 300 Mbps |
| AES-CTR | 800 Mbps 以上 |

加解密是 CPU 密集型操作，主要消耗单核性能。由于本代理会转发全部流量，部署环境的
网络带宽与设备单核性能同样重要。

> 以上为上游记录的数据，本项目未重复实测该项。txiki.js 与 Node.js 的加密后端不同
> （见 [openwrt-tjs-compatibility.md](openwrt-tjs-compatibility.md) 中 C-22 条目），
> 因此实际吞吐可能存在差异。

## 与上游的算法实现一致性

本项目不修改任何加密算法实现。验证方式是与上游 Node 版本做固定向量对照，
覆盖 AES-CTR、RC4-MD5、ChaCha20、MIX、PBKDF2、摘要算法，以及 Range 位置恢复。
两者产出的密文必须逐字节相同，运行记录见 [`../tests/`](../tests/)。
