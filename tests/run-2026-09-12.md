## R-16 逐条对齐

- 目的：确认两侧不存在被"都是 37/37"掩盖的细节差异。
- 方法：按用例编号比对 `status` 与 `detail`，仅归一化天然易变字段（UUID、时间戳目录名、端口）。

## R-17 DAO `getValue` 语义回归（本轮修复）

- 目的：核对 SQLite DAO 替换 NeDB 后是否保持了原版查询语义。
- 现象：用例 A03（缺少 token 的 `/enc-api/*` 请求）得到 `500`，原版为 `401 user unlogin`。
- 首个阻塞点：`node-proxy/src/utils/levelDB.js` 的 `getValue(key)` 直接把 `key` 绑到 SQLite 预处理语句；
  当调用方传入 `undefined`（`getUserByToken(undefined)`）或对象（`getAllFileInfo()`）时，SQLite 绑定失败并抛出，
  而 NeDB 对这类查询返回空结果。
- 修复：`getValue` 在键不是 string/number 时返回 `null`，与 NeDB 的"查不到即空"语义对齐。
- 复验：A03 由 `500` 变为 `401 user unlogin`，与原版一致；R-14 全绿。
- 影响面：该回归只影响鉴权分支（缺失/非法 token 的响应码），不改变加密规则匹配与加解密流程。

## R-20 / R-21 规则形状矩阵（适配版 / 上游原版）

- 目的：复现用户报告的「上传还是明文未加密」，判断是规则写法问题还是加解密逻辑问题。
- 方法：对 13 种 `encPath` 写法逐条执行「真实上传 → **绕开代理**直查原版 AList」，
  逐级核对目录名、文件名与内容是否为密文；含 `enable:false` 与规则不匹配两个负向对照。
- 命令：`ENTRY_SCRIPT=…/rule-matrix.mjs PROXY_KIND=adapted|upstream ALIST_PASSWORD=… node work/api-harness/run-real.mjs`
- 完整输出归档：`work/api-harness/rule-matrix-adapted.log`、`rule-matrix-upstream.log`。
- 日志脱敏说明：上游原版以 `RUN_MODE=DEV` 运行，会把代理**自身**的默认管理口令（`admin` / 项目文档公开默认值）写进日志，
  已在 `rule-matrix-upstream.log` 中替换为 `[REDACTED]`；用户的 AList 凭据从未出现在任一日志中（已按口令关键词核查为 0 命中）。
  适配版以 `RUN_MODE=PROD` 运行，日志中 `password` 字段本就由平台层脱敏为 `[REDACTED]`。
- 判定口径：内容密文头部为 `5a6d07ec9e941af11e1ebebae1b5ea7a` 判为密文；
  明文对照为 `72756c652d6d61747269782d70726f62`（即 ASCII `rule-matrix-prob`）。
- 实际结果（适配版 13 项：密文 7、明文 2、请求被破坏 4）：

| 形状 | 适配版 | 上游原版 |
| --- | --- | --- |
| `/会员/<top>/ARM/.*`（depth 1） | 密文 | 密文 |
| `<top>/ARM/.*` | 密文 | 密文 |
| `ARM.*` | 密文 | 密文 |
| `/会员/<top>/ARM/` | 密文 | 密文 |
| 逗号多规则 | 密文 | 密文 |
| `/会员/<top>/ARM/*` | **请求破坏** | **请求破坏** |
| `/会员/<top>/ARM`（无通配） | **请求破坏** | **请求破坏** |
| `/会员/<top>/ARM/.*`（depth 2） | **请求破坏** | **请求破坏** |
| `/会员/<top>/ARM/*`（depth 2） | **请求破坏** | **请求破坏** |
| 规则不匹配（负向对照） | 明文 | 明文 |
| `enable:false`（负向对照） | 明文 | 明文 |
| **`/会员//<top>/ARM/.*`（双斜杠）** | **密文** | **明文** |

- **13 项中 12 项两侧完全一致；唯一差异是双斜杠规则**：上游把规则按 `//` 原样保存，正则永不匹配 → 落明文；
  适配版在配置保存边界做 `normalizeAlistConfig()` 折叠重复斜杠 → 落密文。这**正是用户报告的现象**，
  且已由适配版修复。
- 两个**上游同样存在**的缺陷（非适配引入，已如实记录而非掩盖）：
  1. **绝对写法会把存储挂载点也加密**。`encPath` 含挂载名（如 `/会员/...`）且形状为 `/会员/<dir>/*`
     或无通配时，`convertRealPath`（`node-proxy/src/utils/commonUtil.js`）取 `pathInfo[0]`（正则**匹配到的文本**）
     按 `/` 切分后只 `shift()` 掉首个空串，其余**每段都加密**，于是挂载名 `会员` 被加密成 `NRpGNCK8u`，
     AList 返回 `failed get storage: storage not found; rawPath: /NRpGNCK8u/.../YwW0G`（HTTP 500）。
     同理，绝对写法在**目录层数 ≥ 2** 时也会触发。
  2. **规则点名的目录本身不会加密**。校验路径不带尾斜杠（`/会员/<dir>` 不匹配 `/会员/<dir>/.*`），
     因此只有其**内容**加密，被点名目录保持明文。
- 机制要点（用于解释上表，非猜测）：`pathFindPasswd` 用 `new RegExp(encPath).exec(url)`，未锚定；
  相对写法（匹配起点在挂载点之下）能保住挂载名，绝对写法会把挂载名一起吃进加密范围。

## 尚未闭环的问题

- 适配版在真实 AList 上**能**正确加密（R-18/R-20 已证）；因此用户报告的「上传落明文」在**规则未命中**时才会出现，
  可归因为：`encPath` 与实际路径形状不匹配、规则被 `enable:false`、或规则含 `//`（旧包/上游行为）。
- 仍缺 guest 证据：以上全部为 Node 侧对照。guest 内实际生效规则需由 `/usr/bin/tjs` 侧复跑确认。
- 下一步定位手段：在 guest 内执行
  `/usr/bin/tjs run /mnt/host/openwrt/alist-encrypt/openwrt-tjs/tests/api-suite-run.mjs`，
  先看输出第一行 `API_RULES`（生效规则回显，密码已脱敏）——若 `encPath` 与上传路径形状不匹配，
  即可直接解释明文落盘；若匹配却仍落明文，才需要排查 txiki 运行时差异。

## 规则写法建议（基于 R-20 实测，非推测）

- 使用**相对写法**（不把存储挂载名写进 `encPath`，或让匹配起点落在挂载点之后），并避免重复斜杠；例如 `会员/ARM/.*` 可用，`/会员/ARM/*` 与 `/会员/ARM` 会破坏请求。
- 由于「规则点名的目录本身不加密」，若要目录名也加密，规则应指向**其父层**或更上层。

## 对照台自身缺陷（非产品缺陷）

- `work/api-harness/shims/tjs-install.mjs` 的 `tjs.serve` 替身把响应头 `content-length` 一并过滤掉，
  导致 C05（WebDAV HEAD 返回明文长度）在对照台上误报失败。真实 txiki 服务端不会丢弃该头。
- 已改为仅过滤逐跳头与 `set-cookie`，`content-length` 原样透传；C05 通过。
- C03 的失败同属误报：WebDAV 的 `href` 按规范是百分号编码形式，断言需先解码再比对。
- 新增矩阵脚本自身的两处缺陷（均为工具问题，已修）：
  1. `new URL(rawUrl)` 对真实 AList 返回的相对直链 `/p/...?sign=...` 抛 `Failed to parse URL`，
     导致首轮 10 项全部记为 ERROR；改为 `new URL(rawUrl, alistOrigin)`。
  2. 逐级核对时只取 `entries[0]`，当规则导致「同一逻辑目录出现明文与密文两份」时会走错分支；
     改为记录该层全部条目并在多于一条时置 `levelAmbiguity`，不再「择一认定为真相」。
- `run-real.mjs` 的 `customEntry` 分支此前只计算未使用，自定义入口仍会因缺少 `API_SUMMARY` 被判失败；已补齐。
